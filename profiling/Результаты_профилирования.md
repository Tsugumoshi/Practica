# Результаты профилирования demo_program.py

Исследование восьми инструментов профилирования Python (раздел 2.3 отчёта).
Среда замеров: Python 3.12, Linux x86-64, однопоточный запуск кроме yappi.
Абсолютные значения зависят от оборудования; относительные соотношения устойчивы.

## 1. timeit — точечные замеры скорости

| Функция | Среднее время вызова | Прогонов | Суммарно |
|---|---:|---:|---:|
| `fib_recursive(30)` | 123 333,50 мкс | 5 | 0,6167 с |
| `fib_iterative(10000)` | 1 523,82 мкс | 100 | 0,1524 с |
| `matrix_multiply(200)` | 1 923,61 мкс | 10 | 0,0192 с |
| `sieve_of_eratosthenes(100000)` | 12 885,86 мкс | 10 | 0,1289 с |
| `memory_churn()` | 1 798,67 мкс | 100 | 0,1799 с |

Разница между `fib_recursive(30)` и `fib_iterative(10000)` — примерно **81 раз**,
при том что итеративный вариант обрабатывает вход в 333 раза большей длины.
Вывод: замена алгоритма важнее любых микро-оптимизаций.

## 2. cProfile — общая картина выполнения

`fib_recursive(30)`:

- всего **2 692 538 вызовов** функций (из них 1 примитивный) за **0,504 с**;
- на `fib_recursive` (demo_program.py, строка 14) приходится **0,504 с** чистого
  времени — 100 % общего времени программы, что подтверждает сложность O(2^n).

## 3. line_profiler — построчная детализация

`fib_recursive(20)`: строка `return n if n < 2 else fib_recursive(n-1) + fib_recursive(n-2)`
— **21 891 срабатывание, 100,0 % времени функции**. Оптимизировать нужно не условие,
а сам алгоритм (см. `fib_iterative`).

`sieve_of_eratosthenes(100000)`: два оператора внутреннего цикла (создание `range`
и присваивание `s[j] = False`) — **47,1 % + 47,3 % ≈ 94,4 % времени** функции.

## 4. tracemalloc — снимки памяти

Для 50 итераций `memory_churn()`:

- текущее потребление после цикла: **1,59 KiB**;
- пиковое потребление: **3 110,63 KiB (≈ 3,04 MiB)**;
- топ прироста между снимками — `demo_program.py:43` (создание списков в
  `memory_churn`), остаток +72 B: временные объекты освобождены сборщиком мусора.

Вывод: рост памяти между снимками мал благодаря GC, поэтому для поиска утечек
важно смотреть именно **пиковое** потребление и сравнение снимков.

## 6. yappi — многопоточный код (clock_type=cpu)

Три потока `worker` выполняли `fib_recursive(10)`, `fib_recursive(11)`,
`fib_recursive(12)` соответственно:

- `fib_recursive`: **929 вызовов** суммарно, ttot **0,000793 с** CPU-времени;
- статистика по потокам: Thread 1 — 0,000515 с, Thread 2 — 0,000396 с,
  Thread 3 — 0,000323 с, MainThread — 0,000471 с.

cProfile не различает потоки и показывает только суммарное время; yappi даёт
разрез по каждому потоку, что необходимо для анализа многопоточных программ.

## 7. py-spy — диагностика без изменения кода

Команда: `py-spy record -o profiling/flame.svg --duration 5 -- python profiling/spin.py`

- подключение к уже запущенному процессу (`ptrace`), код не модифицировался;
- за 5 секунд собрано **499 сэмплов** (100 Гц), ошибок — 0;
- построен flame-graph: `profiling/flame.svg`.

## 8. Scalene — комплексный профиль (CPU + память)

Команда: `scalene run profiling/scalene_demo.py --outfile profiling/scalene_report.html`

- общее время — **786,1 мс**, максимум памяти — **9,899 MB**;
- строка `import numpy` (загрузка NumPy и нативный код): **17 % Python /
  56 % native / 3 % system**, пик памяти 6 MB;
- `fib_recursive` (строка 14): **2 % Python / 11 % native**;
- внутренний цикл решета (строки 38–39): 1–2 % Python;
- итоговое списочное включение (строка 40): 2 % Python, 99 % пиков памяти строки.

Scalene различает код Python и нативные C-функции (NumPy), поэтому видно, что
большая часть времени — нативные вычисления.
