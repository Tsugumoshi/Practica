# Регламент технического обслуживания

**Система: программа «Сумма чётных чисел Фибоначчи» (fibonacci_even_sum)**
**и модуль резервного копирования (backup_restore)**

Версия: 1.2
Репозиторий: <https://github.com/Tsugumoshi/Practica>

---

## 1. Паспортная часть и общие положения

### 1.1. Назначение документа

Регламент определяет план, периодичность, содержание работ и зоны
ответственности специалистов при техническом обслуживании (ТО) проекта.
Цели внедрения регламента:

- минимизация простоев и предотвращение потери данных проекта;
- обеспечение работоспособности программы после каждого изменения;
- единый, повторяемый порядок действий при плановых работах и сбоях;
- сохранность истории изменений за счёт системы контроля версий.

### 1.2. Область применения

Правила регламента распространяются на:

- исходный код `src/fibonacci_even_sum.py` и `src/backup_restore.py`;
- автоматические тесты каталога `tests/`;
- документацию каталога `docs/` и файлы `README.md`;
- примеры данных `examples/`;
- архивы резервных копий каталога `backups/`;
- рабочие сценарии профилирования каталога `profiling/`.

### 1.3. Роли участников

| Роль | Обязанности |
|---|---|
| Инженер по сопровождению | Выполнение плановых работ по технологическим картам, регистрация сбоев, восстановление данных |
| Администратор репозитория | Обслуживание GitHub: ветки, коммиты, проверка CI, откат версий |
| Руководитель практики | Контроль качества работ, приёмка результатов, утверждение изменений регламента |

### 1.4. Виды технического обслуживания

- **Плановое (профилактическое) ТО (ППР)** — календарные работы для
  предотвращения сбоев (раздел 2.1).
- **Внеплановое (инцидентное) ТО** — аварийные работы при возникновении
  ошибок или отказов (раздел 2.2).

## 2. Технологические карты ТО

### 2.1. Плановое (профилактическое) ТО

#### Карта ППР-1. Резервное копирование данных

| Параметр | Значение |
|---|---|
| Наименование операции | Полное резервное копирование данных проекта |
| Периодичность | Ежедневно |
| Вид ТО | Плановое (ППР) |
| Используемые инструменты | Python 3.10+, модуль `backup_restore.py`, свободное место на диске |

Пошаговый алгоритм:

1. Открыть терминал в корневом каталоге проекта.
2. Выполнить команду `python src/backup_restore.py backup . backups`.
3. Убедиться, что в каталоге `backups/` появился архив вида
   `backup_ГГГГММДД_ЧЧММСС.zip`.
4. Записать имя архива в журнал выполненных работ.

Ожидаемый результат: архив создан, команда вернула код 0 и сообщение
«Создана копия: ...».

#### Карта ППР-2. Проверка целостности копий

| Параметр | Значение |
|---|---|
| Наименование операции | Проверка целостности резервных копий по SHA-256 |
| Периодичность | Еженедельно, а также после каждого копирования |
| Вид ТО | Плановое (ППР) |
| Используемые инструменты | Python 3.10+, модуль `backup_restore.py` |

Пошаговый алгоритм:

1. Открыть терминал в корневом каталоге проекта.
2. Выполнить `python src/backup_restore.py verify backups/ИМЯ_АРХИВА.zip`.
3. Проверить вывод: сообщение «Копия целостна.» и код 0.
4. При сообщении «Копия повреждена!» — перейти к карте ИНЦ-2.

Ожидаемый результат: состав файлов совпадает с манифестом, SHA-256 всех
файлов подтверждена.

#### Карта ППР-3. Прогон автоматических тестов

| Параметр | Значение |
|---|---|
| Наименование операции | Регрессионный прогон автоматических тестов |
| Периодичность | Ежемесячно, а также после каждого изменения кода |
| Вид ТО | Плановое (ППР) |
| Используемые инструменты | Python 3.10+, модуль unittest |

Пошаговый алгоритм:

1. Открыть терминал в корневом каталоге проекта.
2. Выполнить `python -m unittest discover -v`.
3. Убедиться, что выполнено 51 тест и все пройдены (вывод `OK`).
4. Дополнительно проверить оформление кода: `black --check src tests`.

Ожидаемый результат: `Ran 51 tests ... OK`; `black --check` не находит
отклонений.

#### Карта ППР-4. Проверка целостности репозитория

| Параметр | Значение |
|---|---|
| Наименование операции | Контроль целостности истории версий Git |
| Периодичность | Еженедельно |
| Вид ТО | Плановое (ППР) |
| Используемые инструменты | Git |

Пошаговый алгоритм:

1. Выполнить `git fsck --full`.
2. Убедиться в отсутствии сообщений о повреждённых объектах.
3. Выполнить `git status` — рабочая копия чистая либо изменения
   зафиксированы.

Ожидаемый результат: `git fsck` не сообщает о потерянных или повреждённых
объектах.

#### Карта ППР-5. Контроль окружения

| Параметр | Значение |
|---|---|
| Наименование операции | Проверка актуальности версии Python и зависимостей |
| Периодичность | Ежемесячно |
| Вид ТО | Плановое (ППР) |
| Используемые инструменты | Python, pip, Git |

Пошаговый алгоритм:

1. Выполнить `python --version`; версия должна быть 3.10+.
2. Сверить версию с требованиями `docs/ТЗ.md`.
3. Для инструментов профилирования свериться с `requirements-dev.txt`.

Ожидаемый результат: версия Python в допустимом диапазоне; отклонения
фиксируются и планируются как адаптивное сопровождение.

### 2.2. Внеплановое (инцидентное) ТО

#### Карта ИНЦ-1. Восстановление данных из копии

| Параметр | Значение |
|---|---|
| Наименование операции | Восстановление данных проекта при повреждении |
| Периодичность | По инциденту |
| Вид ТО | Внеплановое (инцидентное) |
| Используемые инструменты | Python 3.10+, модуль `backup_restore.py` |

Пошаговый алгоритм:

1. Зафиксировать признаки сбоя (какие файлы/каталоги повреждены).
2. Выбрать последнюю проверенную копию в `backups/`.
3. Выполнить `python src/backup_restore.py verify backups/ИМЯ_АРХИВА.zip`.
4. Если копия целостна — выполнить
   `python src/backup_restore.py restore backups/ИМЯ_АРХИВА.zip КАТАЛОГ`.
5. Сверить восстановленные файлы с исходными (например,
   `python src/fibonacci_even_sum.py --input examples/input.txt`).
6. Зафиксировать причину и ход восстановления в журнале сбоев.

Ожидаемый результат: данные восстановлены, проверка работоспособности
пройдена.

#### Карта ИНЦ-2. Повреждённая резервная копия

| Параметр | Значение |
|---|---|
| Наименование операции | Действия при отрицательном результате проверки копии |
| Периодичность | По инциденту |
| Вид ТО | Внеплановое (инцидентное) |
| Используемые инструменты | Python 3.10+, Git |

Пошаговый алгоритм:

1. При сообщении «Копия повреждена!» исключить архив из использования.
2. Создать новую копию картой ППР-1 от текущего состояния данных.
3. Проверить новую копию картой ППР-2.
4. Если повреждение повторяется — проверить диск и окружение, при
   необходимости восстановить код из Git (`git status`, `git checkout`).

Ожидаемый результат: получена целостная копия; причина повреждения
зафиксирована.

#### Карта ИНЦ-3. Откат версии при критической ошибке

| Параметр | Значение |
|---|---|
| Наименование операции | Откат к работоспособной версии кода |
| Периодичность | По инциденту |
| Вид ТО | Внеплановое (инцидентное) |
| Используемые инструменты | Git, unittest |

Пошаговый алгоритм:

1. Убедиться, что ошибка воспроизводится прогоном картой ППР-3.
2. Найти последний исправный коммит: `git log --oneline`.
3. Выполнить `git revert ИДЕНТИФИКАТОР_КОММИТА` (или `git checkout`).
4. Повторить прогон тестов — 51 тест должен быть пройден.
5. Зафиксировать инцидент и решение в журнале сбоев.

Ожидаемый результат: работоспособная версия восстановлена, тесты пройдены.

#### Карта ИНЦ-4. Диагностика производительности

| Параметр | Значение |
|---|---|
| Наименование операции | Профилирование при жалобах на скорость или память |
| Периодичность | По инциденту |
| Вид ТО | Внеплановое (инцидентное) |
| Используемые инструменты | timeit, cProfile, tracemalloc (встроенные, `profiling/`) |

Пошаговый алгоритм:

1. Воспроизвести проблему на демо-программе `profiling/demo_program.py`
   или на реальном сценарии.
2. Выполнить `python profiling/run_benchmarks.py` — замеры timeit,
   cProfile, tracemalloc.
3. При необходимости выполнить отдельные замеры: время — `python -m timeit
   -n 10 -s "from profiling.demo_program import fib_iterative"
   "fib_iterative(10000)"`; память — средствами tracemalloc из
   `run_benchmarks.py` (снимки и `get_traced_memory()`).
4. Сравнить с эталонными замерами `profiling/Результаты_профилирования.md`.
5. Внести исправление, повторить замер и прогон тестов.

Ожидаемый результат: узкое место локализовано, показатели не хуже
эталонных, тесты пройдены.

## 3. Контроль качества и отчетность

### 3.1. Параметры контроля

Качество обслуживания и стабильность системы оцениваются по метрикам:

| Параметр | Целевое значение | Способ контроля |
|---|---|---|
| Успешность прогона автоматических тестов | 51/51, вывод `OK` | Карта ППР-3 |
| Соответствие код-стайлу (black) | 0 отклонений в `black --check` | Карта ППР-3 |
| Целостность последней копии | «Копия целостна.» | Карта ППР-2 |
| Возраст последней копии | Не более 24 часов | Сравнение имени архива с датой |
| Эталонный результат программы | 4 000 000 → 4 613 732 | Запуск на `examples/input.txt` |
| Целостность истории Git | Нет ошибок `git fsck` | Карта ППР-4 |
| Время восстановления после инцидента | Не более 1 рабочего дня | Записи в журнале сбоев |
| Актуальность документации | Документы соответствуют коду | Проверка при каждом изменении |

### 3.2. Порядок фиксации выполненных работ

1. Каждая плановая операция фиксируется записью: дата, операция,
   исполнитель, результат.
2. Каждый инцидент фиксируется записью: дата, симптом, причина, действия,
   результат, превентивные меры.
3. Изменения кода и документации фиксируются коммитами Git с пояснением;
   CI-сценарий GitHub Actions автоматически проверяет тесты и код-стайл
   при каждом push.
4. Результаты обслуживания отражаются в отчёте по практике.
